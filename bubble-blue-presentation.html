02 — COUCHE TRANSPORT

L2CAP vs RFCOMM vs GATT

Le parallélisme est le critère décisif pour BB

L2CAP CoC
  • Envoi parallèle vers N voisins CDS
  • Overhead : 4 bytes seulement
  • MTU : 512–1021 bytes
  • Compatible BT Classic ET BLE
  • Abstraction naturelle Wi-Fi/5G
  • Contrôle de flux par crédits
  • 5 voisins CDS = 10 ms latence
RFCOMM
  • BT Classic uniquement
  • Flux série — pas de paquets délimités
  • Overhead : 8 bytes
  • Max 30 canaux (vs 65535 TCP)
  • Pas d'équivalent Wi-Fi ou 5G
  • Migration multi-transport = impossible
  • Utile uniquement pour debug
GATT
  • Modèle requête-réponse sérialisé
  • MTU : 20 bytes par défaut
  • 5 voisins CDS = 500 ms latence
  • Attendre ACK avant prochain paquet
  • MTU négociable jusqu'à 247 bytes
  • Headers ATT supplémentaires
  • Conçu pour IoT capteurs — pas MANet

Gestion des clés de groupe — 3 options
Option A — Clé statique partagée
  • Simple, overhead zéro
  • 1 membre compromis = groupe entier compromis
  • Pas de forward secrecy · Révocation impossible
Option B — Session key par paquet (Phase 1)
  • Forward secrecy parfaite
  • Révocation : exclure du key header
  • Overhead : N × 32 bytes (≤ 15 membres OK)
  • 5 membres = 160 B · 10 membres = 320 B · 20 membres = 640 B
  • Key rotation périodique → anti-replay multihop
Option C — ECDH éphémère (Phase 2)
  • Overhead constant — indépendant de N
  • Forward + backward secrecy
  • Latence ECDH au join/leave ~50 ms
  • Contribution originale mesurable
